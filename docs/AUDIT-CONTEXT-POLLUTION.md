# 审计补充：推演层污染执行层（M0-b / v0.9.29）

> 缘起：制作研究博文录制时，为录到「真实文本逐字流出」反复与系统较劲，撞出一个**产品层面的真问题**——不只是录制脚本的障碍。
> 核心发现：起草类任务（草稿即产物）在正常点路流程里 3/3 被误判成「缺数据」→ clarify，零文本产出；而 curl 直连同一任务一次成功。
> 这不是模型笨，是**推演层的动作语义错误地传导成了执行层的数据依赖**。
> 审计日期：2026-11-19。代码落点：`prototype/backend/task_tracker.py`、`backend/server.py`、`index.html`。

## 0. 一句话结论

**问题 1 是项目「双向断链」假说的一个新实例**：这次断的不是「语义进展没在路径留痕」，而是「推演器猜的做法（查/检索）污染了执行层对用户真实意图的判断」。它直接威胁到 P2 的成立条件——因为 P1–P4「全绿仅对起草类成立」这个前提，在真实用户路径上其实不成立。

## 1. 铁证（真实后端 + 真实 LLM，2026-11-19）

复现脚本 `test_repro_task_kind.py`，同一 context（起草团队协作指南），唯一变量是 execute 消息里的 label/steps：

| 路径 | label / steps | 结果 |
|------|--------------|------|
| **A 污染路**（正常点路流程的 payload） | `先查资料/检索口径` + `检索口径→整理资料→核对来源` | **clarify=True**，零产出，反问「请说明团队使用的协作工具和技术栈」，31s |
| **B 中性路**（curl 直连 / 中性化） | `直接给出成果` + `[]` | **done**，96 tokens / 3.6s，直接产出条款 |
| 判定 | — | ✅ 铁证成立：根因在 label/steps 注入，不在任务本身 |

制作博文时 `record_demo.js:89-98` 被迫手工把 context/label/steps 中性化（`setContext(CLEAN_CTX)` + `c[0].label='直接给出成果'; c[0].steps=[]`）才录到 done——这个「绕过」动作本身就是问题的旁证。

## 2. 根因：第 5 条诚实规则 × 推演动作语义的叠加

改动前 `AgentExecutor.execute`（`task_tracker.py`）把前端传来的 label/steps 原样拼进 prompt：

```
用户的问题：{context}
用户选择的做法：{candidate_label}          ← 推演器给的「先查资料/检索口径」
已规划的做事顺序：{steps}                  ← 「检索→整理→核对」
...
5. 如果任务需要具体数据或信息而用户没有提供…以 [需要输入: 开头索要。
```

推演器给起草类任务配的动作词几乎都带「查/检索」意味（`检索国内…`、`先查资料/检索口径`）。模型读到「用户选择的做法=查资料 + 顺序=检索→核对」，再叠加第 5 条「需要数据则索要」，于是把**起草任务误判为数据分析任务**，诚实索要输入 → clarify。

> 机制诊断：断链点在 `startExecution` → `execute` 的消息构造——推演层的「怎么做」被当成执行层的「用户要什么数据」。第 5 条本身是对的（诚实机制不能删），错的是它的触发语境被污染。

## 3. 三个问题（按重要性）

### 问题 1 · 推演层污染执行层（关键）
起草类任务在正常点路流程大概率到不了 done，直接威胁 P2 成立条件。见 §1–§2。

### 问题 2 · 连续 clarify 对普通用户是死胡同
协议把 clarify 定义为合法第四态（模型主动索要输入，诚实）是对的。但连点三次「走向这条路」三次都被反问、零产物落地——**这正是用户最初那句「没有实质进展」的另一种形态**：不是 86% 剧场了，而是被诚实机制卡在原地。系统缺「任务类型识别 → 选择执行策略」的门控，也缺连续 clarify 后引导补数据/换做法的产品化路径。

### 问题 3 · 结果卡点击命中不稳（小）
录制脚本点到达牌投影坐标后 `resultCard.shown=false`，但正文已在 DOM。诊断（`test_arrival_click_diag.js`）证实：
- 坐标投影**无误**（worldPos==localPos，deltaPx=0）；
- 命中判定**无误**（`rayHitsAt` 返回 `branchId=-2`）；
- 真正原因：`postDriveArrival` 执行完成后**自动展示**结果卡，脚本再点到达牌触发 toggle 把它**收起** → `shown=false` 但正文仍在 DOM。是「自动展示 × toggle」的语义冲突，非命中区 bug。

## 4. 修复（v0.9.29）

### 4.1 后端任务类型门控（问题 1 核心）
`task_tracker.py` 新增 `classify_task_kind(context)`，三分类：

| 类型 | 识别信号 | 执行语境 |
|------|---------|---------|
| `compose` | 起草/撰写/写一份 + 指南/方案/条款/文档…；强起草动词 | 动作词中性化（检索式 →「按用户要求直接产出成果」）、**不注入 steps**、第 5 条降级为「除非明确要求基于某份拿不到的数据，否则不得索要输入」 |
| `analysis` | 根据/基于…数据、分析/统计/找出…数据、ERA5/S2/CSV… | 原语义，真的缺数据时仍诚实 clarify |
| `general` | 其余 | 原语义（改动前逻辑逐字保留） |

设计纪律：
- **保守识别**：只有明确起草信号才归 compose；宁可漏判（走原行为）也不错判（该索要时不索要，避免编造）。
- **门控在后端**（prompt 在此组装），保证 Web 点路 / 键盘 / curl 直连**全入口一致**——这是「单一真相源」，不在前端重复判断，避免两处漂移。
- **只改语境判断，不碰是否真实调 LLM**：起草类仍是真实单步流式生成，无剧场、无编造。
- `task_kind` 随 `execute_done` 回传，纳入 P1 逐轮账本可核对。

前端 `startExecution` 支持 `opts.forceCompose`（连续 clarify 后主动切换起草策略时传 `task_kind:'compose'`）；后端仍自动识别兜底，直连也受保护。

### 4.2 连续 clarify 产品化引导（问题 2）
- 会话级 `_clarifyStreak` 计数（按 detail 对象去重，非 clarify 收尾/新提问清零）。
- 连续 ≥2 次 clarify：澄清卡显示引导条——「若任务其实不需要外部数据（起草/写作），可直接按起草方式重试；若确实依赖数据请补充」+ **「✎ 按起草方式重试（不要数据）」**按钮。
- 按钮：剥离历次 `[用户补充]` 段回到原始任务 → `_clarifyStreak=0` → `startExecution(idx,{forceCompose:true})` 真实执行。这是产品化出路，不是绕过机制。

### 4.3 结果卡幂等打开（问题 3）
- 新增 `__cockpit.openResultCard()` 幂等钩子（已开则不动，不 toggle）。
- `record_demo.js` 改用它，消除「自动展示后被脚本点收起」的假命中。
- 新增幂等打开后，3D 点击「点开/再点收起」的真人交互语义**保持不变**。

## 6. 对研究结论的影响

- **P2 成立条件修正**：研究里「P1–P4 全绿仅对起草类成立」需补一句限定——**在任务类型门控（v0.9.29）之前，起草类在真实点路流程里也不成立**（被误判为缺数据→clarify）。门控后起草类才真正在正常路径成立。
- **「双向断链」假说新增实例**：原指「语义进展没在路径留痕」；本次是「推演层动作标签错误污染执行层语境判断」。共同的病根是**层间语义没有被纪律性隔离**——推演的「可能做法」不该被执行的「意图判断」当成事实。
- **诚实机制的边界**：clarify 本身是 P1/P4 资产（不编造、主动交互），不能因「卡住用户」而删除。正确的产品化路径是**前置的任务类型门控**（减少误触发）+ **后置的引导出路**（真卡住时给方向），而不是关掉诚实。
- **M1/M2 实验口径**：opaque/transparent 两组的执行层必须一致；本次门控改的是「给模型的语境」，两组同等受益，不影响 A/B 对照效度。
