# 研究问题 PROBLEM

> 目的：把用户那句「界面上感觉没有实质性进展」从一个模糊感受，固化成一个**可检验的研究问题**，并给出工作定义、问题分解与范围边界。
> 前置：[EVIDENCE.md](EVIDENCE.md) 已确立「四轮迭代全在呈现层 + 第五次反馈指向执行层」这条实证；本文件在此基础上追问「那到底什么才算实质性进展」。

## 1. 研究对象

> 概念坐标：本研究是**跨学科**的——学科 1（向量空间上下文可视化）与学科 2（3D 路径空间人机交互展示）的交叉，学科载体、检验问题与「双向断链」机制见 [SUBDISCIPLINES.md](SUBDISCIPLINES.md)。本文件保持学科中立（P1–P4 是联合判据）。

研究的对象不是「3D 驾驶舱长什么样」，而是：

> **在一个用表征界面（3D 驾驶舱）呈现智能体工作的产物里，用户在什么条件下能感知到「实质进展」而非「形式进展」？**

这里有几个要拆开的词：

- **驾驶舱（cockpit）**：本项目原型是一个把智能体的岔口探索、候选选择、任务执行用 3D 路牌／载具／任务挂件可视化的界面。它是一个**表征（representation）**——它不直接做任务，它呈现任务。
- **实质进展 vs 形式进展**：这是全文的核心区分，见 §4 的工作定义。
- **感知（perceive）**：研究落点不是「客观上有没有进展」，而是「用户能否在界面上把它认出来」。两者可以分离——执行层可能真的推进了，但界面没让用户感知到。
- **学科坐标**：这个「表征」横跨两个学科——语义空间（学科 1：智能体上下文的真实结构变化）与路径空间（学科 2：3D 里的工作位移）。下文所有判据（P1–P4）都是跨学科联合的，而非任何单一学科的内部标准。

**关键空白**：所有证据都证明了「呈现层做到头了」，但**没有任何一条证据回答「那什么才算实质进展」**。这正是把这个空白做成研究问题的理由——现在所有「加功能」「再优化」的冲动，都因为没有定义而无法判断对错。

## 3. 核心张力

这个研究之所以不是「加个功能」能解决的，是因为存在一个真正的张力：

> **看得见的（呈现层）和真正推进的（执行层）之间，缺少一座能让用户感知到的桥。**

具体表现为三组矛盾：

1. **表征丰富 vs 状态未变**。3D 做得再绚烂，用户的实际任务状态（那份报告、那个模型、那次验证）有没有被真正推进？如果没，界面越丰富，反差越大——「看起来动得很多，实际上我没得到东西」。
2. **执行真实 vs 不可感知**。执行层（RAG、工具调用、验证）可能真的在干活，但它在界面上是黑盒。用户只看到脚手架，看不到「这一步真的改变了我的东西」。
3. **开发冲动 vs 无验收标准**。每一次「我觉得该这么做」的开发冲动，都因为没有「实质进展」的度量而无法被证伪——做完了也说不清算不算推进了。这正是「拍脑袋继续开发」的机制根源。

**本研究要消解的张力**：让「实质进展」变得**可定义、可感知、可度量**，从而让后续每一轮开发都有一个先于实现的验收标准。

## 4. 工作定义（把「实质性进展」操作化）

这是本文件最重要的产出。给「实质性进展」一个**操作性定义**，而不是停留在形容词：

> **实质进展 = 界面让用户感知到「用户的某个真实任务状态，因这个智能体的工作，发生了可核对、可追溯的改变」。**

拆成四个必须同时满足的判据（缺一则退化为形式进展）：

| 判据 | 含义 | 反例（形式进展） |
|------|------|------------------|
| **P1 真实性（real）** | 改变发生在用户的**真实任务/产物**上，不是界面内部自嗨 | 只更新了路牌颜色，用户那份报告一个字没动 |
| **P2 可核对（verifiable）** | 用户能自己确认这个改变是真的 | 界面说「已完成」，但看不到产物、看不到依据 |
| **P3 可追溯（attributable）** | 用户能知道**是谁/哪一步**带来的改变 | 进度条动了，但说不清是智能体哪一步起的作用 |
| **P4 可感知（perceivable）** | 这个改变**在界面上可被认出** | 执行层真干了活，但界面没呈现，用户无从感知 |

**核心命题（初版，已被审计修订——见 §5.5 与 §5.6）**：v0.9.9 的失败不在任何一个执行层功能缺失，而在 **P4 缺失**——执行层的进展（如果有）没有在界面上被认出，于是全部退化为「形式进展」。这也解释了为什么呈现层迭代无效：**在 P4 建立之前，往呈现层加的每一处细节，都是对「看不见实质进展」的更多装饰。**

> ⚠️ **2026-11-09 审计修订**：上面的乐观命题**被证伪了一半**。执行链审计（[AUDIT.md](AUDIT.md)）发现中间步骤本就没有真实工作（P1 破损），不只是「有进展但没呈现」。所以第一性问题已从「如何让进展可感知（P4）」升级为「如何让执行链真实（P1）且归因准确（P3）」。运行时实证（[RUNTIME-AUDIT.md](RUNTIME-AUDIT.md)）进一步把「假」精确化为「中间剧场 + 尾部真实」——不是整链假，是中间假（占 ~86% 时长）。详见 §5.5 与 §5.6。

这个命题是**可检验的**：只要构造一个满足 P1–P4 的界面变化，再度量用户的「实质进展感」是否上升，就能验证。这就是 RESEARCH-PLAN.md 要设计的实验。

## 5. 待答问题（分解）

把核心问题拆成一组可独立研究的子问题，附**当前状态**（已答/假设/未知）：

**Q0 定义层**
- Q0.1「实质进展」四判据（P1–P4）是否完备？有没有第 5 个必要判据被漏掉？——状态：**工作假设**，需用户侧数据证伪。

**Q1 诊断层**
- Q1.1 在 v0.9.9 原型里，P1–P4 各自是满足还是缺失？哪一条是用户反馈的真正卡点？——状态：**未知**，需逐条对照原型做审计。
- Q1.2 用户说「没有实质进展」时，内心指的是 P2（看不到可核对结果）、P3（说不清谁做的）还是 P4（没呈现）？——状态：**未知**，三者对应完全不同的修法。

**Q2 机制层**
- Q2.1 为什么呈现层的丰富不能转化为进展感？（假设：进展感的燃料是「界面信号 ↔ 真实状态改变」的**对应性**，而非信号本身的数量/华丽度。）——状态：**假设**。
- Q2.2 「表征 → 感知」的桥是什么？是结果卡、状态锚点、可核对的产物、还是「可信度校准」（让用户确信后台真的跑了）？——状态：**假设候选，待排序**。

**Q3 设计层**
- Q3.1 哪些**界面原语**（result card / 状态锚点 / change-diff / 可追溯回放）能让执行层的实质进展变得可感知？——状态：**待设计实验**。
- Q3.2 这些原语与现有 3D 表征如何共存而不冲突？——状态：**待设计**。

**Q4 度量层**
- Q4.1 如何度量「实质进展感」本身（区别于「界面满意度」或「视觉丰富」）？——状态：**未知，是最硬的问题**。
- Q4.2 用什么指标验收一次开发「是否构成了实质进展」？——状态：**未知，是本项目交付给开发的核心资产**。

### 5.5 审计更新（2026-11-09，首轮证据落地）

第一次把 P1–P4 对照原型**实际代码**打分（完整证据见 [AUDIT.md](AUDIT.md)），结果直接修订了若干问题的状态：

| 问题 | 原状态 | 审计后状态 |
|------|--------|-----------|
| Q1.1 原型 P1–P4 现状 | 未知 | **已审计**：P1 破损、P2 部分、P3 破损、P4 满足但感知到剧场 |
| Q1.2 用户卡点是 P2/P3/P4 哪个 | 未知 | **暂定升级为 P1**：执行链中间步骤本就不真实（新发现，原三选一没这个选项） |
| Q2.1 机制假设 | 假设 | 被强化：对应性假设成立的前提更苛刻了（信号不只是要"对应真实改变"，它对应的改变本身得是真的） |
| Q3.1 界面原语 | 待设计 | **降级**：呈现层实验在 P1 修复前无意义（剧场做得再清楚还是剧场） |

**审计的硬结论（2026-11-09 初版，2026-11-09 §5.6 运行时修正表述）**：执行链中间步骤（rag/tool/generate/verify）不调用 LLM、`_run_task` 的 `prompt` 参数是死参数、进度是 `sleep(0.09)` 睡出来的、`_local_result` 返回模板句——**只有最后一步 output 是真实 LLM 调用**。

> 📌 **§5.6 运行时实证的精确化**：运行时计时（[RUNTIME-AUDIT.md](RUNTIME-AUDIT.md)）证实现网 `task_update` 间隔整齐 90–100ms、零散布——中间步骤把 ~86% 的总时长花在假节拍上；`source=llm` + `chain[-1]=output` 证明尾部那一步是真 LLM。所以准确的因果链是**「中间剧场 + 尾部真实」**，而非「整链是剧场」——这个区分直接决定修法：不是「把整链做真」（大工程），而是要么真做中间步骤（路线 A），要么砍掉剧场降级为单步真流式（路线 B）。

**因此研究第一性问题重排**：
1. **P1（真实执行链）**：中间步骤要么真做（路线 A：真实工具/检索/校验后端），要么诚实降级（路线 B：取消中间剧场，单步真 LLM + 流式 token 逐字流出，进度 = 真实信号本身）。← 新的第一优先级
2. **P3（归因准确）**：展示的进度要与实际工作一一对应。
3. **P2（可核对）**：真实产物要能被用户核对。
4. **P4（可感知）**：在前三者成立后，才谈得上"呈现"。← 降级到最后

这条重排是本项目给开发的第一份实质指导：**别再做呈现层了，先把执行链做真（或诚实降级到真信号）。**

## 6. 可检验性（为什么这是研究，不是感想）

一个主张若不检验，就只是另一种「拍脑袋」。本研究的可检验性来自三点：

1. **工作定义是操作性的**。§4 的 P1–P4 是四条可逐条打分的判据，不是修辞。
2. **命题可被证伪**。§4 的核心命题（P4 缺失导致退化）有一个明确的反例场景：如果执行层本就没有实质推进（P1 都不满足），那么任何界面改造都不会有进展感——这会把问题从「呈现」重新指回「执行」，本身就是有价值的分辨。
3. **实验可构造**。RESEARCH-PLAN.md 会设计「给一个满足 P1–P4 的变化 → 度量进展感」的对照实验，让假设可被证实/证伪。

**诚实的边界**：本项目目前只有开发侧产物（原型代码 + DESIGN.md），**没有用户侧数据**。「用户真正指什么」目前是推断。因此所有 Q1/Q2 的结论都需要一次最小的用户侧验证才能从假设变为结论——这本身写进了计划。

## 7. 范围边界（本项目不做什么）

研究型项目最容易犯的错是范围膨胀。明确划出边界：

**不做**
- ❌ 不直接改原型（那是开发主线，不是本研究）。
- ❌ 不做「再设计一批 3D 特效」——那正是已被 EVIDENCE 判为收益趋零的路径。
- ❌ 不声称在用户没有真实使用数据的情况下给出确定性结论。

**做**
- ✅ 给出「实质进展」的可检验定义（P1–P4）。
- ✅ 审计原型在 P1–P4 上的现状（Q1）。
- ✅ 形成可被开发使用的验收标准与度量方案（Q4）。
- ✅ 用一个最小对照实验，验证「P4 呈现能否带来进展感」。

## 8. 与后续开发的接口

本研究的产出不是代码，是**一个开发前必须过的自检**：

1. 任何一次开发前，先回答：这次要推进的是 P1–P4 中的哪一条？
2. 如果只推进呈现层（不触及 P1–P4），默认视为「未构成实质进展」，需给出理由。
3. 每个里程碑用 Q4 的度量验收，而不是用「看起来好了」。

这条接口让「研究指导开发」落到实处：此后每一轮迭代，都有一个先于实现的、可证伪的判据。
