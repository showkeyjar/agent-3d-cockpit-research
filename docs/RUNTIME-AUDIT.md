# 运行时实证：执行链每步真实耗时测量（2026-11-09）

> 承接 AUDIT.md 静态审计。静态审计结论「中间步骤不调 LLM」语义成立，但需要运行时证据钉死；
> 同时本轮数据**修正了静态审计的一处表述**：不是「整链是剧场」，是「中间剧场 + 尾部真实」。

## 实验方法

- 无头 Chromium 打开原型 → 页面内建独立 WebSocket → 发送 `type=execute`（与用户点「走向这条路」同格式）
- 每条 WS 消息用 `performance.now()` 打时间戳 → 统计 `task_update` 间隔分布
- 两用例：3 步链（检索销售资料并分析）vs 1 步链（汇总各通道数据）

## 实测数据

**3 步链**（18 条事件，总 2626ms）：

```
+312ms  execute_ack / status  执行任务链
逐批 task_update 间隔：313→402→498→608→687→781→2342→2436→2515（约每 100ms 一批）
+2626ms execute_done  source=llm  chain=["generate","generate","output"]
```

**1 步链**（8 条事件，总 2554ms）：

```
+308ms  execute_ack → 单批 task_update → +2554ms execute_done source=llm chain=["output"]
```

**间隔统计**：n=17 中位 79ms；成批次间隔整齐落在 90–100ms。

## 判定（证据链闭环）

| 证据 | 结论 |
|------|------|
| `task_update` 间隔整齐 90–100ms，零散布 | 中间步骤时长由 `sleep(0.09/0.1/0.35)` 节拍构成，无真实 I/O |
| `chain` 为关键词映射的启发式派生（代码 321–356 行） | 任务拆分是本地假动作，不问模型 |
| 中间步骤 `result=None` → `_local_result()` 模板句（代码 425–429 行） | 中间步骤产出是文案模板，不是工作成果 |
| 尾部 `chain[-1]=output` + `source=llm` | **只有最后一步是真 LLM 产物** |
| `_answer()` 在循环前 `create_task`、`i==last` 时 await（408/416 行） | LLM 请求在整个中间阶段并发等待——进度条填的是等待时间 |

## 修正后的最终结论（替代 AUDIT.md 的表述冲击）

- **AUDIT.md 说对**：中间步骤不调 LLM、无真实检索/代码执行、prompt 死参数、进度是睡出来的——**全对**。
- **AUDIT.md 说过**：「整条链呈现的进度大部分是假的」——**修正为**：中间步骤的进度是假的（占整链 ~86% 时长），最后一步的最终答案是真的。
- 用户「没有实质性进展」感的机制 = **剧场进度屏蔽真实等待**：用户看到的是 3 个假步骤逐格填满，真成果只有最后一小段文本。与其说「呈现层没呈现真进度」，不如说「呈现层呈现的是假进度」——两者的修复路径完全不同（前者补呈现，后者砍剧场）。

## 对开发指导的影响

P1「把执行链做真」拆成两条可验收路线：

1. **路线 A（大小工程）**：中间步骤真实执行（真实 RAG/代码执行/校验后端），保留步进式 idle 节奏。
2. **路线 B（低成本）**：**诚实降级为单步链 + 真实 LLM 草稿流式**——取消中间剧场步骤，一个真实请求 + 流式 token 逐字流出，进度 = token 流本身。用户每一刻看到的都是真产物（或真实等待），不再有 fake 步骤。

路线 B 的论证：当前「86% 假进度 + 14% 真成果」让我甄别的是问题，不是进度；去掉假步后，「进度感」自发由 token 流重建。这也是我在 PROBLEM.md §4 修正后的命题落点。

## 复现脚本

`tools/runtime_audit.js`（Playwright + 页面内 WebSocket + performance.now 计时）——

```
node tools/runtime_audit.js
```

前置：原型服务运行在 `http://localhost:8770/`（uvicorn，backend 目录启动）。脚本硬编码了本地 Chrome 与 ws 地址，按需改。

# 路线 B 落地复测（2026-11-11）

> 承接上文：上文路线 B 的论证与验收标准是**设计态**。本节是它落地后的**运行时复测**——同一套测量方法（页面内 WebSocket + performance.now），对照 2026-11-09 的剧场数据。

## 落地方式（原型 v0.9.12）

诚实降级：剧场中间链（`TASK_CHAINS` + `sleep(0.09)` + 模板文案）整段移除，执行链收敛为单步真实 LLM（`/chat/completions` 流式），token 经新增 `token` 事件逐字下发，进度 = 真实输出字数，归因链仅 `["output"]`。

## 复测数据（同一脚本、同一两用例）

**3 步规划链路**（23 条事件，总 2195ms）：

```
+315ms  execute_ack / status
+780ms  首个 token（首 token 延迟 ~465ms）
token/task_update 交替流式：13 个 token 事件，累计 117 字
+2195ms execute_done  source=llm  chain=["output"]
```

**1 步链**（32 条事件，总 2816ms）：

```
19–24 个 token 事件，累计 163–202 字（两次运行），source=llm，chain=["output"]
```

**间隔分布对照**：

| 指标 | 2026-11-09（剧场） | 2026-11-11（路线 B） |
|------|------|------|
| task_update 间隔中位 | 79ms，整齐落在 90–100ms | ~114ms，散布 0–1150ms |
| 整齐节拍指纹 | ✅ 存在（sleep(0.09) 铁证） | ❌ 消失（最大间隔 >1s，为真实首 token 延迟/慢 chunk） |
| token 流覆盖时长 | 无 token 事件 | 占总执行时间 60–70% |
| 进度信号 | sleep 节拍（假） | 已输出字数（真） |

## 判定

| 判据 | 状态 | 证据 |
|------|------|------|
| P1 真实性 | ✅ 修复 | 全程只有一个真实 LLM 请求；token 流即产物本体 |
| P2 可核对 | ⚠️ 有条件 | 见下方「任务类型校准」——起草任务成立，数据分析任务不成立 |
| P3 可追溯 | ✅ | chain=["output"]：单步执行，归因与事实一致（不再暗示多步） |
| P4 可感知 | ⬜ 待用户验证 | 进度条=真实字数属开发侧判定；用户侧感知未测（M0 出声思维） |

### 任务类型校准（2026-11-11，回应 GPT 评审 Finding 1）

「P1–P4 全绿」需按**任务类型**限定，否则会过度声称：

- **起草/生成类任务**（如"起草一份技术方案"）：模型产出的草稿**本身就是交付物**，无外部输入依赖。此时 P2 成立——用户能核对产物是否可用。路线 B 的 P1–P4 全绿**仅对这类任务成立**。
- **数据分析类任务**（如"分析本季度销售数据，找出异常月份"）：结论必须**基于输入数据**才可核对。当前用例**未提供任何销售数据**，模型仍输出"11月销售额环比骤降40%、供应链中断缺货"等具体业务结论——这证明**真实生成发生（P1✓）**，但这些数字**无输入依据、不可复算**，**P2 不成立**。界面若把这些数字当"已完成的分析成果"呈现，反而制造新的不可核对信号。

**结论修正**：路线 B 修复的是**执行链的真实性与归因**（P1/P3），不是**产物的可信度**（P2）。P2 的成立取决于任务是否给了模型可核对的输入。后续实验用例须区分两类任务，数据分析任务须附输入数据 + 可复算口径，否则不得声称 P2。

**结论**：上文「86% 假进度 + 14% 真成果」的剧场结构已被诚实降级消除——不存在假步骤了。用户甄别的对象从「假进度」变成「真实 token 流 + 首 token 延迟」，后者是真等待，可直接感知。

**遗留**：首 token 延迟 ~465ms–1s（模型 prefill），期间界面只有「模型生成中…」——这是真实等待，已属诚实范畴，不构成新的剧场。若后续接路线 A（真实多步工具），须重新按本节方法复测间隔分布。
