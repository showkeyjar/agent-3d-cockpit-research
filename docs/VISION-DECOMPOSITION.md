# 三愿景功能拆分与研究对齐

> 目的：把用户提出的三个愿景，逐个对照研究框架（P1–P4 判据 / 学科归属 / 研究问题 / 剧场风险）做功能拆分，给出**优先级路线、验收标准与实验接口**。
> 定位：本文件是研究/设计产物，指导后继开发，不直接改原型。每个功能都标注它推进了哪条判据、服务哪个研究问题、有什么剧场风险。
> 前置：[PROBLEM.md](PROBLEM.md)（P1–P4 定义）、[SUBDISCIPLINES.md](SUBDISCIPLINES.md)（学科与双向断链）、[RESEARCH-PLAN.md](RESEARCH-PLAN.md)（路线 B 已落地、实验协议）。

---

## 0. 分析框架：每个愿景必须先过的四道关卡

研究的核心警告是：**呈现层精细化已越过收益拐点，只推进呈现层不触及 P1–P4 = 未构成实质进展**。所以每个愿景的功能拆分必须逐条过这四关：

| 关卡 | 问什么 | 不过关的后果 |
|------|--------|--------------|
| **判据关** | 它推进了 P1–P4 的哪一条？ | 答不上来 = 装饰，默认不构成实质进展 |
| **学科关** | 它属于学科 1（向量空间）还是学科 2（路径空间）？ | 单学科自嗨 = 又一次"做了看不见" |
| **断链关** | 它是否在两个空间之间架了桥（双向断链的修复）？ | 架桥 = 修复；只在一个空间内加码 = 断链延续 |
| **剧场关** | 它的内容是真实信号，还是装饰性华丽？ | 假内容 = B2/B3 警告的"沉浸让假进度更可信" |

**三个愿景与研究机制的对应**（这是本文件的分析骨架）：

| 愿景 | 对应的研究机制 | 一句话定位 |
|------|----------------|-----------|
| **愿景 3**（结果具象化 + 联动） | P4 桥 / Q2.2 / P3 归因 | 回答"界面上感觉没有实质性进展"——**最贴合研究核心，应排第一** |
| **愿景 1**（周围向量风景） | 双向断链·学科1侧 / A1–A2 | 修复"语义结构没有在路径空间留下可感知痕迹" |
| **愿景 2**（多模态空间信息） | B2/B3 沉浸放大效应 | **最高剧场风险区**——既是最丰富的真信号，也可能是最可信的剧场 |

> ⚠️ 关键判断：用户列愿景的顺序（1→2→3）不是优先级顺序。按研究的第一性排序（P1→P3→P2→P4，P1 已由路线 B 完成），**愿景 3 先于愿景 1 先于愿景 2**。理由见 §1。

## 1. 愿景 3 优先：结果具象化与联动（最贴合研究核心）

> **定位修订（2026-11-11，用户定调）**：愿景 3 **不是大重构，而是细节优化**。现有原型已具备结果卡、到达标记、任务挂件等基础，要做的是把"联动"和"视野体验"做细，而非重写。因此 §1.3 的拆分以**增量改造**为原则：每个功能都先问"现有代码里有没有半成品"，有则改、无则加，避免推倒重来。

### 1.1 为什么它排第一

三个理由，全部来自研究框架而非主观偏好：

1. **它直接命中用户的真实抱怨**。用户说"联动很不直观，用户不容易感知到"——这句话**就是研究的核心问题陈述**（P4 缺失：执行层真干了活，但界面没让用户认出）。愿景 3 是对"界面上感觉没有实质性进展"最直接的回答。
2. **它对应研究的第一性排序的下一步**。PROBLEM.md §5.6 把第一性问题重排为 P1→P3→P2→P4。路线 B 已完成 P1。下一步是 **P3（归因准确）**——而用户说的"联动"，字面就是归因：结果物件要挂回"是哪一步、哪一条路"产生的它。愿景 3 同时服务 P3（联动/归因）+ P2（可核对）+ P4（可感知）。
3. **它是 M1/M2 对照实验的"处理组"本身**。RESEARCH-PLAN §3 的 B 组（执行透明）= 结果卡 + 可核对产物 + 归因。愿景 3 的结果物件化，就是把这个处理组从"2D 文本卡"升级成"3D 游戏物件"。它先落地，实验才有可测的呈现原语。

### 1.2 现状诊断（对照原型代码）

| 现状 | 代码位置 | 问题 |
|------|----------|------|
| 结果以 **2D DOM 文本卡**呈现 | `showResultCard()` (index.html:2283) | 结果是平铺文字，不是 3D 物件；与路径的视觉关联弱 |
| 任务挂件是 **DOM 投影卡** | `updateTaskWidget()` / `taskAnchor()` (index.html:2641) | 锚定在路段上方，但只是文字卡，游戏感弱 |
| 到达标记是几何体 | `addArrivalMarker()` (index.html:2772) | 有 3D 标记，但和结果内容没强绑定 |
| **联动弱** | 全局 | 结果卡弹出时，3D 里对应的路牌/路段**不亮、不指向、不呼应**——用户看不出"这个结果是哪段路走出来的"。这正是 P3 破损。 |

**根因**：结果（学科1 的产出）和路径（学科2 的载体）之间**没有可感知的绑定**。结果卡是浮在画面上的 DOM，脱离了 3D 空间。这是"双向断链"的学科2侧：路径空间没有承接学科1 的结果。

### 1.3 功能拆分

#### F3.1 结果物件化（Result Objectification）
- **做什么**：把每个任务的真实产出（模型答案、检索到的文档、生成的代码块）渲染成 **3D 游戏物件**，而不是 2D 文本卡。例如：一段文本 → 发光卷轴/数据立方；一张图 → 悬浮图板；一段代码 → 代码方块。
- **服务判据**：P4（可感知）——结果从"文字"变成"空间里的物件"，可被一眼看见。
- **服务研究**：Q3.1（界面原语）、Q2.2（表征→感知的桥）。
- **剧场关**：物件形态是呈现，**内容必须是真信号**（路线 B 的真实 LLM 输出）。物件只是容器，容器再华丽，里面是假内容就是剧场。
- **验收**：物件内容 = `source=llm` 的真实输出；物件可见性测试通过（回归脚本能断言物件存在且内容匹配）。

#### F3.2 强空间锚定（Strong Spatial Anchoring）——"联动"的核心
- **做什么**：每个结果物件**锚定到产生它的那个路径节点/路段**上。到达一个节点 → 该节点的结果物件"亮起/浮出/指向"。物件与路段一一对应，用户能顺着路"捡"结果。
- **服务判据**：P3（可追溯/归因）——**这是"联动"的字面含义**：结果挂回"哪一步、哪条路"。同时 P2（可核对）：物件就在产生它的位置，可核对。
- **服务研究**：直接修复双向断链的学科2侧；服务 H3（归因假设）。
- **剧场关**：锚定关系必须**真实**（物件确实来自该路段的执行），不能随机挂。
- **验收**：到达节点 N → 只有节点 N 的结果物件亮起；点击物件 → 高亮对应路段（可核对）；回归脚本断言锚定关系正确。

#### F3.3 物件交互（Object Interaction）
- **做什么**：结果物件可点击/悬停/旋转查看。悬停 → tooltip 显示摘要；点击 → 展开详细内容（复用现有结果卡的内容，但换到 3D 交互层）。
- **服务判据**：P2（可核对）——用户能主动核对物件内容。
- **服务研究**：Q3.2（原语与 3D 表征共存）。
- **验收**：点击物件能展开其真实内容；不破坏现有结果卡的信息。

#### F3.4 结果星座（Result Constellation）
- **做什么**：走过的多条路的结果物件在空间里**聚成星座/收藏**，形成"我这次探索收获了什么"的可回顾集合。跨会话可回看（复用 `backend/memory.py` 的 journey 持久化）。
- **服务判据**：P4 + 记忆即轨迹（原则3）。让"走了哪些路、拿到哪些结果"可回顾。
- **服务研究**：B1（路径位移可追踪）、记忆回放。
- **验收**：多次探索后，结果星座可见且可点击回看。

#### F3.5 联动反馈（Linkage Feedback）
- **做什么**：结果物件与路径之间的**双向呼应**——到达点亮物件，物件被查看时反向高亮路段，路段走完时物件"就位"。让"做的事"和"看到的路"对上（P4 的联合判据）。
- **服务判据**：P4（把"做的事"与"看到的路"对上）+ P3。
- **服务研究**：核心命题——补上 P4 后进展感是否上升。**这正是 M1/M2 实验要测的**。
- **验收**：联动动画可被感知（不是一闪而过，用户正在看 3D 时能接住——呼应 v0.9.12.1 的教训：一次性脉冲感知窗口只有 1.4s）。

#### F3.6 视野体验（View Experience）——"在空间中运动"的感受
- **做什么**：用户说"在空间中运动时的视野体验还有待加强"。这是**细节优化**维度：现有相机系统已具备司机追逐镜、orbit/pan、复位、VR 立体（index.html:3536 `driverCam`、`resetCamera`），**能力不缺**，缺的是运动中的**感受质量**。拆为三个子项：
  - **F3.6a 行驶视野层次**：行驶中视野里只有路牌、四周是黑虚空 → 补**景深/雾效/地面网格延伸/远山剪影**等环境层次，让"在路上"有空间纵深感（不是悬浮在虚空里）。环境元素必须**锚定真实空间结构**（如地面网格 = 实际路径平面），不是飘浮贴图。
  - **F3.6b 运动速度感**：用户"自由行动"时的速度反馈——速度线/FOV 微缩/加速度感（相机跟随的阻尼曲线调优，呼应 index.html:916 已有的阻尼插值）。**速度 = 真实执行速度**（token 流速率），不是装饰性速度。
  - **F3.6c 到达/转向的镜头反馈**：到达节点、转向分叉时，镜头给一次**可感知的微反馈**（轻微推进/抬升/环绕），而非无反馈直行。这是 P4 的"到达可被感知"在镜头层的落点。
- **服务判据**：P4（运动中的进展可感知）+ 原则4（速度即掌控）。
- **服务研究**：这是愿景3 与愿景1 的**交汇点**——视野体验同时服务"在路径空间运动"（学科2）和"看见周围风景"（学科1）。
- **剧场关**：环境层次/速度感是**呈现**，但必须锚定真实空间与真实速度；纯装饰性贴图 = 剧场。
- **验收**：行驶中视野有环境纵深（可截图断言非纯黑虚空）；速度反馈与真实执行速度对应；到达时镜头有可感知微反馈。

#### F3.7 视野信息密度控制（View Information Density）
- **做什么**：视野里的信息不能过载。用户在空间中运动时，哪些该看、哪些该淡出、哪些该隐藏（呼应 index.html:1393 已有的"挡视野的牌主动隐身"逻辑）——把"视野管理"从临时补丁升级为**系统性原则**：前方主干信息常驻、周围风景按需淡入、结果物件到达时才浮现。
- **服务判据**：P4（可感知且不喧宾夺主）。
- **剧场关**：淡出/隐藏的信息必须是**真实存在但暂不相关**，不能是假信息被藏起来。
- **验收**：行驶中视野信息分层清晰，无遮挡；关键信息（路牌、到达）始终可感知。

#### F3.8 视野与结果的联动（View-Result Linkage）
- **做什么**：F3.2 联动在**镜头层**的延伸——到达节点时，镜头**自然转向**结果物件出现的位置，让用户"顺着镜头看到结果落下"。这是 F3.2（强空间锚定）+ F3.6（视野体验）的**合成**：结果不只是亮起，而是**被镜头带到用户眼前**。
- **服务判据**：P4（结果→感知的桥）+ P3（归因）。
- **服务研究**：Q2.2（表征→感知的桥）的镜头层实现。
- **验收**：到达节点 → 镜头转向结果物件位置 → 物件亮起，三者连贯可被感知。

### 1.4 愿景 3 小结
- **学科归属**：学科1（结果）× 学科2（路径）的**交叉桥**——这正是它最有价值的地方，它同时动两个空间。
- **定位**：**细节优化**（用户定调），不是大重构。F3.1–F3.5 是"联动做细"，F3.6–F3.8 是"视野体验做细"。
- **优先级**：**第一**。
- **核心风险**：物件化是呈现，容易滑向"把文字卡换成 3D 卡但内容不变、联动不变"的纯视觉升级。**必须**以 F3.2（强空间锚定/联动）为骨架，物件化只是外壳。视野体验（F3.6–F3.8）同理——**锚定真实空间/速度/结果**，否则就是又一次呈现层迭代。

## 2. 愿景 1：周围向量风景（学科1 的可感知化）

### 2.1 定位与概念澄清

愿景1 要解决"只有主干显示，其他是黑色的虚空"——用户想在向量空间里自由行动时，看到**相邻/相似的上下文向量**（沿途风景或分叉）。

**概念问题（必须先澄清）**：这个向量空间**是谁的**？
- 研究框架里，向量空间是**智能体上下文**的语义空间（学科1）。
- 用户说"用户操作大模型在可视化向量空间里自由行动"——这是让**用户**进入**智能体**的上下文空间去导航。
- 这是一个**新的研究问题**：上下文空间的用户可导航性。它把学科1 从"呈现给开发者看"变成"让用户进去探索"。

**建议的设计立场**：向量空间 = 智能体上下文 + 候选走向的语义空间。用户"自由行动"= 在这条语义风景里移动视角/载具。风景（周围向量）= 与当前上下文相邻/相似的真实语义对象。

### 2.2 现状诊断

| 现状 | 代码位置 | 问题 |
|------|----------|------|
| 只有**候选**被投影到 3D | `force_directed_3d()` (projection.py:32)、`applyForecastResult()` | 只显示岔路的 K 个候选，**候选之外的上下文向量是虚空** |
| embedding 用**哈希伪向量** | `_hash_embed()` (llm_forecaster.py:451) | 有真实文本相似性（共享表述→向量相近），但不是真语义向量；`_embed_api()` 已写好但需独立 embedding 模型 |
| 邻域/密度无渲染 | 无 | 没有"周围风景"，只有孤零零的岔路 |

### 2.3 功能拆分

#### F1.1 上下文向量场渲染（Context Vector Field）
- **做什么**：把**整个上下文**（不只是候选）的向量渲染成空间里的风景点/雾/地形，而不是只有岔路。当前上下文 = 向量空间的中心地带，候选 = 岔路。
- **服务判据**：P4（学科1 的语义结构可感知）。
- **服务研究**：A1（语义空间结构进展能否被感知）。
- **剧场关**：风景必须来自**真实 embedding**。若用哈希向量，必须**如实标注"近似"**，不能假装是真语义。
- **数据依赖（关键决策点）**：
  - 方案 A：接真实 embedding API（`_embed_api` 已实现，需 embedding 模型）。风景 = 真语义。
  - 方案 B：保留 `_hash_embed`，但**诚实标注**为"文本相似性近似，非真语义向量"。
  - **研究原则要求诚实**——选哪个都行，但标注必须真实。这本身是一个可检验的诚实降级。

#### F1.2 邻域感知（Neighborhood Perception）
- **做什么**：与当前上下文向量**相邻/相似**的对象作为"近处风景"高亮，远处淡化。用户移动时，风景随当前位置的邻域变化。
- **服务判据**：P4 + 学科1 结构可感知。
- **服务研究**：A1（簇间最小距离、多样性能否被感知）。
- **验收**：相似的对象在空间里确实靠近（可被断言）；用户能区分"近邻"和"远邻"。

#### F1.3 空间密度地形（Spatial Density Terrain）
- **做什么**：向量密度 → 地形（密的地方 = 山/亮区，疏的地方 = 谷/暗区）。让上下文的"语义稠密区"肉眼可见。
- **服务判据**：P4（结构变化可认出）。
- **服务研究**：A2（上下文是否被真实重构，而非装饰性扩张）——密度地形是重构的可见证据。
- **剧场关**：密度必须来自真实向量分布。

#### F1.4 自由探索（Free Exploration）
- **做什么**：用户不只沿主干行驶，可以**自由移动视角/载具**浏览向量风景（悬停、环视、缩放，复用现有相机系统）。
- **服务判据**：P4 + 掌控感（原则4 速度即掌控）。
- **服务研究**：这是新的交互范式，本身值得研究——用户进入智能体上下文空间的体验。
- **验收**：自由浏览不破坏现有行驶流程；可作为独立模式。

#### F1.5 灵感触发（Inspiration Trigger）
- **做什么**：用户看到相邻/相似的向量时，触发"启发"——例如提示"这条路附近有和你任务相关的上下文"。这是愿景1 的"对研究的任务有启发"落点。
- **服务判据**：P4 + P2（启发 = 用户能核对这个相关上下文确实存在）。
- **服务研究**：Q2.2（表征→感知的桥是否带来启发）。
- **剧场关**：启发必须基于**真实的邻域相似性**，不能是随机弹出。

### 2.4 愿景 1 小结
- **学科归属**：学科1（向量空间）为主，但**必须**通过学科2（路径空间）呈现——这正是修复双向断链的学科1侧。
- **优先级**：**第二**（在愿景3 之后）。
- **核心风险**：
  1. **embedding 数据依赖**：没有真 embedding，"风景"就是近似/装饰。必须做 §2.3 F1.1 的决策点。
  2. **自由探索 vs 主干行驶的冲突**：愿景1 要自由行动，现有原型是沿主干行驶。这是交互范式的扩展，不能破坏现有三阶段流程。

## 3. 愿景 2：多模态空间信息（高剧场风险，需门控）

### 3.1 定位与剧场风险警示（最重要）

愿景2 要"图片、声音、视频都立刻呈现在用户面前，比起任何 EDA 工具都来的**震撼**和直接"。

⚠️ **"震撼"是研究明确警告的语言**。PROBLEM.md / EVIDENCE.md 的核心结论是：**呈现层的华丽度不是进展感的燃料，信号↔真实状态的对应性才是**（H1.1）。用户在这里用了"震撼"，恰好命中 B2/B3 警告的"沉浸让假进度更可信"。

**但愿景2 不是全错**——它有一个**正当内核**和一个**危险外壳**：
- **正当内核**：如果图片/声音/视频是**智能体真实产出/检索的多模态内容**（真信号），那它是 P2（可核对）的强载体——用户能直接核对真实多模态产物。尤其"走偏检测"是真实的感知信号。
- **危险外壳**：如果多模态内容是**装饰性素材**（为了震撼而贴图），那它是**最可信的剧场**——越震撼，用户越以为有实质进展，实则没有。

**门控原则**：愿景2 的一切功能，内容必须 = 真实多模态产出；否则不做。

**内容来源已确定（2026-11-11）**：由用户拍板"先用一个小的开源多模态模型试试"，已部署 **Qwen2.5-VL-3B-Instruct**（GGUF Q4_K_M + mmproj，llama-server :8083）。这意味着：vision 层的"真实多模态内容"可以从**本机真实跑 VLM** 得来（对图像做描述/OCR/理解），而不是只能用智能体检索的现成素材。这同时给了愿景2 两个真实信号源：① 智能体真实产出的多模态内容；② 本机 VLM 对图像实时生成的描述（P2 可核对）。**能力边界**：3B 模型做"描述/OCR/简单问答"够用，做复杂推理会出错——设计上不要让它承担高难度任务，出错时诚实呈现"描述可能不准"。

**生成模型的角色（2026-11-11 补充，用户提问触发）**：

Qwen2.5-VL-3B 是**理解模型**（看图说话），它只能描述已有图像，**不能凭空生成**多模态内容。而愿景2 要的是"图片、声音、视频立刻呈现在用户面前"——如果智能体执行任务时需要**产出**一张概念图/示意图（比如"画一张示意图说明这个概念"），理解模型做不到，需要**生成模型**。

但这恰恰是研究框架要严格门控的地方。生成模型的正当用法 vs 危险用法：

| 用法 | 性质 | 判据 |
|------|------|------|
| 生成模型作为智能体的**真实工具**：任务需要多模态产出时，智能体调用生成模型完成，产出被呈现为"智能体画的图" | **真信号**（P2 可核对：生成过程可追溯、同 prompt 可复现） | 可核对、可追溯 |
| 生成模型生成**装饰性素材**：为了"震撼"而自动贴图，产出被伪装成"检索到的真实素材" | **剧场**（假信号，比装饰更危险——它看起来最真实） | 不可核对 |

**结论**：生成模型**值得部署**，但必须满足两个条件：① 作为智能体的真实工具被调用（不是自动装饰）；② 产出被诚实标注为"AI 生成"（可核对、可追溯）。否则宁可不做。

**候选与部署路径**：
- **SDXL-Turbo**（2.6B，Q8_0 GGUF 4GB，4-6步出图，~15秒/张）：成熟稳定，stable-diffusion.cpp 原生支持 Vulkan，与 llama.cpp 同生态（都是 C++ 原生引擎，无需 Python）。本机剩余显存 ~9-10GB 可跑。
- **FLUX.2 klein 4B**（4B，Q4 ~2.6GB，4步出图，Apache 2.0）：更现代、许可更干净，但 GGUF 生态尚不成熟（Comfy-Org 仓库只有 safetensors）。
- **推荐**：SDXL-Turbo（成熟度优先）。部署方式：stable-diffusion.cpp（Windows Vulkan 版）+ SDXL-Turbo GGUF。
- **音频/视频生成**：本机无轻量方案，**诚实降级**——音频暂不支持，视频仅支持图像序列。

**✅ 生成模型已部署并实测通过（2026-11-11）**：
- **引擎**：stable-diffusion.cpp（`leejet/stable-diffusion.cpp` master-465adf3），Windows Vulkan 版，安装于本机工具目录（示例：`<tools>/sd-cpp`）
- **模型**：SDXL-Turbo `sd_xl_turbo_1.0.q8_0.gguf`（3.81GB，Q8_0 量化），置于该引擎目录下 `models/`
- **服务**：sd-server 端口 **1234**，Vulkan 后端，auto-fit 将全部组件（DiT 2925MB + Conditioner 835MB + VAE 160MB ≈ 3.9GB）装入 Vulkan0 显存
- **API**：`POST /v1/images/generations`（OpenAI 兼容格式），参数：`prompt`/`negative_prompt`/`width`/`height`/`steps`/`cfg_scale`/`sampler_name`/`seed`；Turbo 模型 `cfg_scale=1.0`、`steps=5`
- **实测**：1024×1024 出图 ~15秒，返回 3.1MB PNG，HTTP 200
- **与现有服务共存**：8082（35B 文本）+ 8083（VL-3B 理解）+ 1234（SDXL-Turbo 生成）三服务并行，显存余量充足
- **关于理解模型（8083）的定位**：用户判断"理解模型有点多余"基本正确——生成模型才是愿景2 主线，理解模型降级为辅助（仅 F2.3 走偏检测的弱用途）。保留不删除（已部署已测试，不花钱），后续显存紧张可停掉释放 ~3GB

### 3.3 功能拆分（全部带门控）

#### F2.1 多模态物件锚定（Multimodal Object Anchoring）
- **做什么**：真实的图片/音频/视频内容，锚定到它们在向量空间的模态层位置（复用 MOD_LAYER 的 y=0/6/12/18 分层）。图片内容来源：① 智能体真实检索/产出的图像；② **本机 Qwen2.5-VL-3B 实时生成的图像描述**（作为 vision 层的可核对文本信号，锚定在 vision 层）；③ **本机 SDXL-Turbo 生成的图像**（当智能体任务需要"画一张图"时，调用生成模型真实产出，锚定在 vision 层）。音频/视频同理，但音频目前无本地模型，**诚实降级为暂不支持**或仅用文本描述占位。
- **服务判据**：P2（可核对）——用户能直接看到/听到真实多模态产物。
- **服务研究**：Q3.1（界面原语）、学科1 的模态维度。
- **⚠️ 门控**：内容必须是智能体**真实产出/检索**的多模态内容，或 VLM **真实生成**的描述，或生成模型**真实生成**的图像。**装饰素材 = 剧场，拒绝**。VLM 描述要标注来源（"本机 Qwen2.5-VL-3B 生成，可能不准确"）；生成模型产出的图像要标注"AI 生成"（可核对、可追溯）。
- **验收**：物件内容可核对为真实来源；模态层位置与内容模态一致；VLM/生成模型产出标注来源与不确定性。

#### F2.2 模态分层可视化升级（Layer Visualization Upgrade）
- **做什么**：把 MOD_LAYER 从"抽象淡环"升级为"真实内容层"——每一层是该模态的真实物件集合，层与层之间有空间关系。
- **服务判据**：P4（模态结构可感知）。
- **服务研究**：学科1 的模态维度可感知化。
- **⚠️ 门控**：同 F2.1。

#### F2.3 走偏检测（Deviation Detection）——愿景2 的正当内核
- **做什么**：用户能通过周围信息**发现自己走偏了**。实现：当前路径与上下文簇质心的相似度衰减 → 周围风景变暗/变色/提示"偏离主簇"。
- **服务判据**：P4 + P2——走偏是**真实感知信号**（相似度确实下降），用户能核对。
- **服务研究**：B1（路径位移真实性）、A1（结构可感知）。**这是愿景2 里最有价值的部分，因为它是真信号，不是装饰。**
- **剧场关**：走偏判定必须基于**真实相似度计算**，不能随机。
- **验收**：人为构造走偏 → 周围信息确实变化；相似度计算可被断言。

#### F2.4 启发触发（多模态版）
- **做什么**：多模态邻域触发启发（与 F1.5 呼应，但跨模态）。
- **服务判据**：P4 + P2。
- **⚠️ 门控**：启发基于真实跨模态相似性。

### 3.4 愿景 2 小结
- **学科归属**：学科1（模态维度）× 学科2（空间呈现），但**呈现权重高**，剧场风险最高。
- **优先级**：**第三**（在愿景3、愿景1 之后）。
- **核心风险**：这是唯一一个**用户主动用"震撼"描述**的愿景。研究要求我们在这里最严格地自检：**内容是真信号吗？还是装饰？** 若无法保证真实多模态内容，宁可只做 F2.3（走偏检测）这一个正当内核，也不做"震撼"外壳。
