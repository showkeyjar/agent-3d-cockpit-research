# 研究计划 RESEARCH-PLAN

> 目的：把 [PROBLEM.md](PROBLEM.md) 分解后的问题，翻译成一份**可执行、可验收**的研究计划——假设清单、方法论、实验协议、里程碑。
> 定位：本计划的产出不是代码，而是一套「开发前自检 + 验收度量」，让后继每轮迭代都有一个先于实现的判据。

## 0. 一句话路线

**先审计原型在 P1–P4 上的现状 → 再做执行链真实化/诚实降级（路线 A/B 决策）→ 然后用对照实验验证「P4 呈现能否带来进展感」→ 最后把结论固化成开发可用的验收标准。**

四件事有先后依赖：不审计就设计实验，实验会建立在错误假设上；实验前不把执行链做真/降级，两个自变量（执行真实 vs 界面呈现）会纠缠在一起，H2 无法归因（见 §2.3 的剧场污染论证）。

## 1. 假设清单（可证伪）

每个假设都写成可被证伪的形式。状态标记：**[待验]** = 尚未有数据。
所有假设都是**跨学科联合假设**（学科 1 × 学科 2 联合判定）；学科下钻（A1–A2 / B1–B3）见 [SUBDISCIPLINES.md](SUBDISCIPLINES.md)。

**H1 对应性假设（机制层，对应 Q2.1）**
- H1.1 进展感的燃料是「界面信号 ↔ 真实状态改变」的**对应性**，而非信号本身的数量/华丽度。
  - 证伪方式：若呈现信号数量/华丽度与进展感正相关，而对应性无关，则 H1.1 被推翻。
  - 状态：**[待验]**
- H1.2（v0.9.43 补充）把**真实内部状态信号**（MoE 聚合专家路由指纹）编码进 3D 并呈现，提升内部维度的进展感/信任/追溯（对应 f1–f3）。
  - 证伪方式：B（显示指纹环）vs B2（隐藏）的 f1–f3 无系统差异，则 H1.2 被推翻；装置见 M-EXPERIMENT §2d。
  - 诚实边界：专家 ID 无名，只测"看到线索及感受"，不宣称可解释性。
  - 状态：**[待验]**（装置已就绪，真人 B−B2 对照待做）

**H2 呈现假设（设计层，对应 Q3.1 / 核心命题）**
- H2.1 在执行层已真实推进（P1 满足）的前提下，补上 P4 呈现（结果卡 + 可核对产物 + 归因），用户的「实质进展感」显著高于不呈现。
  - 这是全文要检验的主命题。
  - 状态：**[待验]**
- H2.2 仅补呈现、执行层并未真实推进时，进展感**不会**真正上升（会停留在「看起来做了」的怀疑里）。
  - 这是 H2.1 的镜像，防止「装饰品实验」把结论做空。
  - 状态：**[待验]**

**H3 归因假设（对应 Q2.2 / Q1.2）**
- H3.1 用户说「没有实质进展」时，主要卡点是 P3（说不清谁/哪一步带来）或 P2（看不到可核对产物），而非 P1。
  - 若成立，修法指向「归因 + 可核对结果」，而非继续加执行产物。
  - 状态：**[待验]，需用户侧数据**

## 2. 方法论

采用「**审计 → 最小用户验证 → 对照实验 → 固化验收**」四步。前两步是预备，第三步是主证据，第四步是交付。

### 2.1 静态审计（对原型）
- 拿 PROBLEM.md §4 的 P1–P4 四判据，逐条对照 v0.9.9 原型的**实际行为**打分（满足/缺失/部分）。
- 证据来源：读原型代码（执行链 `execute` / 结果卡 / 记忆回看）+ DESIGN.md，不靠印象。
- 产出：一张「原型 × P1–P4」现状矩阵，明确**卡点在哪一条**——这决定实验该补哪条。

### 2.2 最小用户验证（对「用户指什么」)
- 因为目前只有开发侧产物、无用户侧数据（PROBLEM.md §6 已声明这个缺口），必须先补一次最小验证。
- 方式优先级：**① 真实用户出声思维（think-aloud）跑 2–3 个真实任务 → ② 代理被试（开发/同事）代替，结论降级为「假设」**。
- 要回答的就一个问题（Q1.2）：用户说「没有实质进展」时，内心指向 P2 / P3 / P4 的哪一个。
- 产出：对 Q1.2 的有数据支撑（或明确标注「代理被试，待真实用户确认」）的回答。

### 2.3 执行链真实化（P1 前置决策，路线 A/B）

> 由运行时实证（[RUNTIME-AUDIT.md](RUNTIME-AUDIT.md)）发现：当前执行链 = 中间剧场 + 尾部真实。§3 实验要分离「执行层真实」与「界面呈现」两变量，**前提是执行链中间不再有剧场**——否则 A/B 组的执行层都是假的，实验只能测出「剧场呈现 vs 无剧场呈现」，测不出「真实推进 vs 产出」本身。

两条路线（开发按成本谈判，二选一后进入 §2.4 实验）：

| 路线 | 做法 | 成本 | 验收 |
|------|------|------|------|
| **A 真实执行中间步骤** | rag/tool/generate/verify 接真实后端（检索库/代码执行/校验），保留步进节奏 | 大 | 每次 task_update 间隔不整齐（有真实 I/O 散布），产物可核对 |
| **B 诚实降级单步流式** | 取消中间剧场步骤；一个真实 LLM 请求 + token 流式逐字流出，进度=token 流 | 小 | 无 fake 步骤；用户全程看真实 token；无 90ms 整齐节拍 |

- 路线 A 适合：中间步骤确有真实价值（如检索确实影响答案质量），且能谈下工程预算。
- 路线 B 适合：中间步骤本身的价值存疑时——直接删掉，把「进度感」重建在真实信号（token 流）上。
- **判定原则**：优先路线 B（成本最低、最快逼近「真信号」），除非路线 A 的中间步骤有明确不可替代的产出价值。

> ✅ **路线 B 已于 2026-11-11 在原型落地（v0.9.12）**，验收通过（详见 [RUNTIME-AUDIT.md](RUNTIME-AUDIT.md) 路线 B 复测节：token 流 60–70% 覆盖、90–100ms 整齐节拍指纹消失）。**验收结论的限定（2026-11-11 GPT 评审后校准）**：路线 B 修复的是执行链的真实性与归因（P1/P3），"P1–P4 全绿"仅对**起草/生成类任务**成立；数据分析类任务若无输入数据，模型产物不可核对（P2 不成立）。§2.4 对照实验的执行层前提已满足。

### 2.4 对照实验（主证据）
- 用一个受控实验直接检验 H2.1 / H2.2。协议见 §3。
- 这是把「呈现能否带来进展感」从哲学讨论变成可测量事实的关键一步。
- **前置条件**：实验用例须在路线 A 或 B 落地后的执行链上构建（§2.3），否则两个自变量纠缠，结论不可归因。

### 2.5 固化验收（交付）
- 把实验结论 + 审计结论，浓缩成一张 **「实质进展验收清单」**：开发任何新特性时，先回答它推进了 P1–P4 的哪条。
- 这张清单是本项目交给开发主线的核心资产（对应 Q4.2）。

## 3. 实验协议（检验 H2）

> 目的：分离「执行层真实推进」与「界面是否呈现」两个变量，看进展感随哪个变。

### 3.1 变量
- **自变量**：界面呈现方式（透明执行 vs 不透明执行）。
- **因变量**：实质进展感得分（量表见 §3.4）。
- **学科归属**：呈现原语（结果卡/可核对产物/归因）= 学科 2 路径空间原语；执行层真实推进（路线 A/B 完成后的链）= 两学科共同底座的「被呈现物」——实验检验的是**联合判据**（P1–P4），不是单一学科内部指标。
- **控制变量**：任务内容、执行层真实工作量、被试类型、界面视觉风格尽量一致。

### 3.2 分组（2×1，被试间）
| 组 | 执行层 | 界面呈现 | 检验 |
|----|--------|----------|------|
| A 对照组（执行不透明） | 真实完成任务 | 只显示「智能体思考中…」流动动画 + 结束「已完成」 | H2.1 的基准 |
| B 实验组（执行透明） | 真实完成任务（**与 A 同量**） | 显示结果卡 + **可核对产物** + **归因（哪一步）** | H2.1 的正向 |

- 两组执行层**都真实推进**（P1 都满足），唯一差别是 P2/P3/P4 的呈现。
- 这样若 B 进展感 > A，差异只能归因于「呈现」，而非「执行更多」——干净分离。

### 3.2b 最小对照：单独归因 3D 联动（2026-11-11 GPT 评审补充）

> 原 §3.2 的 B 组同时加入结果卡、可核对产物、归因三个呈现维度，**无法单独回答「结果卡 ↔ 到达节点」的 3D 联动贡献了多少**——三者纠缠。在投入完整 A/B 前，先做一个**最小对照**：

| 组 | 输出 | 结果卡 | 等待时序 | 唯一差异 |
|----|------|--------|----------|----------|
| B0 | 同一份真实输出 | 同一套结果卡 | 相同 | 结果卡**不**与到达节点联动（点定位按钮无 3D 响应） |
| B1 | 同一份真实输出 | 同一套结果卡 | 相同 | 结果卡**与**到达节点联动（F3.2 双向锚定） |

- 这样 B1−B0 的差异**只能归因于联动本身**，把 3D 联动从「整套透明呈现」里剥出来。
- **行为结果记录**（在 s1–s5 量表之外）：① 能否找到产物；② 能否指出对应步骤；③ 能否复述一条可核对依据。
- 保留 s5 主观评分作主指标，行为结果作客观佐证。
- **范围声明**：B0/B1 两组执行都真实，因此本最小对照只覆盖 **H2.1**（呈现能否带来进展感）的实验范围；**H2.2**（呈现≠真实推进时不虚高）保留为待验，需另设执行未真实的镜像组。

### 3.3 程序
1. 给被试一个**真实任务**（例如「帮我起草一份关于 XX 的简短技术方案」），让智能体真实执行（确实产出内容）。
2. 被试观察执行过程（A 组只见流动动画；B 组见结果卡 + 产物 + 归因）。
3. 任务结束后，被试填量表（§3.4）。
4. 记录耗时、是否注意到产物、是否相信「真的做了」。

### 3.4 测量量表（实质进展感）
区分于「界面满意度」「视觉丰富」，条目逐一对应 P1–P4（李克特 1–7 分）：

| 条目 | 对应判据 | 测量什么 |
|------|----------|----------|
| s1 我相信这一步**真正推进了我的任务** | P1 真实性 | 是否相信发生了真实改变 |
| s2 我能**确认结果是真实可核对的** | P2 可核对 | 是否能看到/验证产物 |
| s3 我知道**是哪一步/谁**带来这个改变 | P3 归因 | 归因清晰度 |
| s4 我**在界面上注意到了**这个改变 | P4 呈现 | 呈现可感知性 |
| s5 整体上我感到产生了**实质进展（而非只是看起来忙）** | 总体 | 实质进展感主指标 |

- 主指标 = s5；机制指标 = s1–s4。
- 预期（H2.1）：B 组 s5 显著 > A 组，且主要体现在 s2/s3/s4 上升。
- 预期（H2.2）：若另设 C 组「只呈现、执行未真实推进」，C 组 s5 不应真正上升、s1 会偏低——作为镜像对照（可选，样本够时加）。

### 3.5 统计与诚实标注
- 样本量小时（如 n<5/组），不做显著性声明，只报告方向 + 明确「样本不足」。
- 被试为代理（开发/同事）时，结论标注「代理被试，待真实用户确认」。

## 4. 风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| 无真实用户数据 | 结论是推断 | 最小用户验证兜底；代理被试则降级标注 |
| 新奇效应（B 组因界面新鲜而得分高） | 高估呈现效果 | A 组界面也用同一套视觉，只是**不呈现实质内容**；把「新鲜感」从「实质呈现」里剥出来 |
| 任务难度混淆进展感 | 归因不清 | 各组用同一批任务、随机分配顺序 |
| 归因错觉（用户归因于自己） | P3 度量失真 | 量表 s3 明确问「谁/哪一步」，B 组给明确归因线索 |
| 实验做成「装饰品」 | 结论空转 | 强制保留 H2.2 镜像组，确保呈现≠真实推进时不虚高 |

## 5. 里程碑与验收标准

每个里程碑有**可核对的验收标准**——不靠「做完了」。

**M0 审计 + 最小验证（预备）**
- 验收：产出「原型 × P1–P4 现状矩阵」；完成 ≥1 例用户侧出声思维（或代理被试，标注降级）；对 Q1.2 给出有数据（或降级标注）的回答。
- 出口：知道实验该补哪条判据。
- 进度（2026-11-11）：✅ 现状矩阵（AUDIT.md）；✅ 执行链前置决策执行完毕——路线 B 已落地并运行时验收（RUNTIME-AUDIT.md 复测节），§2.4 实验的执行层前提已满足；⬜ 最小用户验证（Q1.2 出声思维）尚未做（但 M-EXPERIMENT §4 三类任务 + §5 访谈流程已把 Q1.2 采集口径固化，待真人数据填入）。
- **M0 任务设计要求（2026-11-11 GPT 评审补充）**：出声思维任务须区分两类——① 起草类（草稿即产物，验证 P2 成立路径）；② 数据分析类（**必须附输入数据**，如"基于这份给定数据找出异常并指出依据"），另设**缺数据版本**观察界面能否准确传达"缺少输入"而非编造结论。后者直接检验路线 B 的 P2 边界。

**M1 测量 + 实验协议定稿**
- 验收：§3.4 量表定稿（条目对应 P1–P4）；对照组/实验组可跑通的最小脚本；明确被试来源。
- 出口：实验可被复现地执行。
- 进度（2026-11-13）：✅ §3.4 量表已定稿；✅ 可运行协议 `docs/M-EXPERIMENT.md`（含三类任务脚本 T1 起草 / T2 数据分析(附数据) / T3 缺数据版、A/B 操作定义、程序时间线、数据 schema、M3 清单模板、被试来源与伦理）；✅ 自包含采集工具 `tools/m-instrument.html`（知情同意→随机分配→s1–s5+3 行为结果→M3 自动清单→localStorage+导出 JSON/CSV）；✅ 原型加 `?mode=opaque` 使能 A 组（仅隐藏 P2/P3/P4 呈现层，真实执行与「思考中…」动画保留，3D 不变量/中断态零回退）。被试来源见 M-EXPERIMENT §10（真实用户优先，代理被试降级标注）。

**M2 对照实验执行**
- 验收：完成 A/B 两组实测；报告 s1–s5 组间差异；样本不足则如实声明。
- 出口：H2.1 得到证实/证伪 + 证据强度标注。

**M3 结论 + 验收清单交付**
- 验收：产出「实质进展验收清单」（每条特性标注推进了 P0–P4 哪条）；回写 PROBLEM.md 状态（哪些假设转正/被推翻）；更新 README 状态。
- 出口：开发主线拿到可先于实现自检的资产——本项目使命达成。
- **进度（2026-11-19）**：✅ 清单本体已交付 `docs/M3-ACCEPTANCE.md`——判据从 P1–P4 扩为 **P0（结果可用性）→P4**，每条带可复算核验、四级证据标注（静态/运行时/代理/真人）、开发自检模板、未闭合项诚实清单。**尺子已交付，数据待填**：所有判据行标【真人】待验，M2 真人数据进来前不得宣布 M3 完成（见该文件 §5 交付定义）。
  - ✅ **装置层状态已回写（2026-11-19）**：`docs/PROBLEM.md` §5 待答问题状态、`README.md` 当前状态节、`docs/RESEARCH-PLAN.md` §6 均已对齐至 v0.9.43 的客观事实（实验三组对照 + 激活信号支线的装置/运行时证据）。

## 6. 与开发的接口（一句话）
