### 0.1 与最初三条核心要求的差距

用户最初的要求是：① 后端在提问前推演可能走向，差异小走直道、差异大分岔；
② 任务执行可视化为 3D 挂件，能看到后台在做什么；③ 驾驶前认知对齐，白话路牌，看不懂可解释。

| 初心 | v0.7 之前的问题 | v0.7 的修复 |
|---|---|---|

### v0.9.10 研究同步：执行链真实性审计注记（2026-11-09）

> 本节不是交付记录，而是**研究审计结论回写**。研究项目（本仓库）：根目录 `docs/` 为研究背书（`PROBLEM.md` 给出 P1–P4 工作定义，`AUDIT.md` 给出完整证据），`prototype/` 为实证原型代码。**原型代码未变**——本节只修正历史表述、校准认知，并给出后续开发优先级。

**审计方法**：拿 P1–P4 四判据（真实性/可核对/可追溯/可感知）逐条对照 `backend/task_tracker.py` 与 `backend/server.py` 实际代码打分，不靠印象。

**核心发现：执行链中间步骤是「剧场」**

| 判据 | 状态 | 证据（可复核） |
|------|------|----------------|
| P1 真实性 | ❌ 破损 | `_run_task` 体内 `self._llm` 调用次数 = 0；`execute()` 中只有 `i == last`（output 步）才取 `_answer()` 的真实结果；中间步骤 `result=None` → 走 `_local_result()` 模板句 |
| P2 可核对 | △ 部分 | 只有 output 步 `source==='llm'` 时结果卡显示真实正文；否则显示「执行记录」（即剧场链的记录） |
| P3 可追溯 | ❌ 破损 | 展示链 rag→generate→output 暗示每步都做了事，实际只有最后一步调了模型；归因与事实不符 |
| P4 可感知 | ✓ 满足 | 进度条会动、结果卡会出现——但被感知的「进展」是演出链，不是真实进展 |

**三条硬证据**：
1. **`prompt` 是死参数**：`_run_task(task_key, prompt, ...)` 的 `prompt` 在函数体内从未被使用——`_task_prompt()` 为每个任务类型生成的 prompt 全是死代码，从不发给模型。
2. **进度是睡出来的**：中间步骤进度推进靠 `asyncio.sleep(0.09)` 循环，不是真实工作。
3. **无真实后端**：全文件不存在向量库/检索/代码执行后端；`rag` 的脚步名称（RAG·查询中…/召回 Top-K…/重排序…）是纯展示。

**对历史表述的勘误**：§0.3 v0.6 档案「每个子任务真实调 LLM」是当时的目标陈述，当前代码不成立（见该处勘误注记）；§0.2 诚实清单「本地确定性流程」措辞偏轻，精确表述为「中间步骤未执行任何检索/代码/校验」。

**为什么这解释了「界面上没有实质性进展」**：用户看到的「检索知识库→生成中间结果→输出」进度链，除了最后一格，前面每格什么都没干。不是「真干了但没呈现」，是**呈现的进度大部分是假的**。四轮呈现层迭代（v0.9.6–v0.9.9）之所以无效，根因在此。

**后续开发优先级（研究项目给出，本原型已采纳为约束）**：
1. **P1 真实执行链**（第一优先级）：中间步骤要真的干实事（接真实工具/检索/校验，或诚实降级为「直接回答」单步链），而非演出
2. **P3 归因准确**：展示的进度要与实际工作一一对应
3. **P2 可核对**：真实产物要能被用户核对
4. **P4 可感知**：在前三者成立后，才谈得上呈现层

→ 呈现层新特性（3D 特效、车队、沉浸）默认冻结，除非挂到 P1–P3 的真实推进上。

## 0. v0.1 → v0.2 的关键升级

v0.1 是"静态 3D 壳"，地图是前端摆好的。v0.2 的三条纠正把它变成**真正改变后端工作方式**的系统：

| 纠正 | 含义 | 影响范围 |
|------|------|---------|
| ① 后端前瞻推理 | 不是前端静态摆路，而是后端在用户下次输入前**主动推演所有可能走向**；走向相似→直道，走向差异大→分岔 | **后端推理流程** + 路生成 |
| ② 任务执行挂件 | 后台真正在跑的活儿（工具调用/agent 行动/数据处理）浮成 3D 挂件，状态进度一目了然 | 后端任务追踪 + 前端可视化 |
| ③ 认知对齐 | 开车前先对齐认知，生成**用户看得懂的路牌**；看不懂一键要白话解释，确认后才出发 | 新增前置阶段 |

**核心结论升级**：3D 高速不是装饰，它是**后端前瞻推理分歧度（divergence）的直接可视化**。路长什么样，由后端推演出的"可能走向"决定——这是 v0.2 与普通 3D 聊天壳的根本区别。

## 1. 核心命题

**当前智能体交互的根本问题不是"信息太少"，而是"信息没有空间结构"。**

传统对话框是线性时间轴：每轮问答压扁成气泡，前文折叠、后文未生成。用户无法"预看"，每次决策都要停下来等——像"只看得见车头前 2 米"的驾驶，效率极低。

**类比：用大模型 = 在向量空间里开车。**
- 上下文是一条有预设分支的信息高速公路；
- 每次输入是选择"驶入哪条车道"；
- 输出是沿选定方向"往前铺路"。

既然本质是**空间导航**，就该用**空间界面**承载。人脑处理 3D 视觉的带宽远高于线性文本序列——**把"序列式等待"变成"并行式预览"。**

## 2. 设计原则（v0.2 扩展为七条）

| # | 原则 | 含义 |
|---|------|------|
| 1 | **空间即进度** | 位置 = 完成度，不必读文字就知道走到哪 |
| 2 | **前瞻即决策** | 前方路标/分支预渲染，决策在生成前完成 |
| 3 | **记忆即轨迹** | 走过的节点形成空间轨迹，可回看回溯 |
| 4 | **速度即掌控** | 用户能调速/暂停，始终握方向盘 |
| 5 | **道路即分歧（新增）** | 3D 路形 = 后端前瞻推理的分歧度，不是装饰 |
| 6 | **挂件即后台（新增）** | 后台任务浮成挂件，所见即所做 |
| 7 | **路牌即认知（新增）** | 路牌必须用户看得懂，看不懂一键白话 |

## 3. 完整交互模型：三阶段驾驶流程

```
┌─────────────────────────────────────────────────────────┐
│ 阶段一：认知对齐 (ALIGN)                                  │
│   目标 → 生成路标(术语+白话) → 用户确认看懂 → 出发        │
└───────────────────────────┬─────────────────────────────┘
                            ▼
┌─────────────────────────────────────────────────────────┐
│ 阶段二：前瞻推理 (FORECAST)                               │
│   后端推演所有可能走向 → 算分歧度 → 直道/缓弯/分岔         │
│   → 路形动态生成 → 出发                                   │
└───────────────────────────┬─────────────────────────────┘
                            ▼
┌─────────────────────────────────────────────────────────┐
```

### 3.1 阶段一：认知对齐（ALIGN）

**目的**：开车前先让"导航"和"驾驶员"对齐认知。路牌是给用户看的，所以必须先生成**用户看得懂**的标牌。

- 后端把目标/上下文解析成一组**路标（Sign）**，每块路标含：
  - **术语**：模型内部的技术标签（如 `tool_call:rag_retrieval`）
  - **白话**：用户能懂的解释（如"这一步会去翻资料库找相关信息"）
- 前端把路标铺在"出发区"前，用户逐块看。
- **看不懂 → 一键点击 → 弹出白话解释浮层**。
- 用户确认全部看懂 → 点击"确认对齐" → 进入前瞻推理。

> 本质：这是一个**可解释性前置层**。它把模型内部状态翻译成人话路牌，避免用户"看不懂路牌还硬开"。

### 3.2 阶段二：前瞻推理（FORECAST）

**这是 v0.2 的核心，后端工作方式的根本改变。**

**问题**：用户下一次输入还没发生，但驾驶不能等。怎么办？后端**主动把上下文所有可能的走向先推演一遍**。

**流程**：
1. **候选采样**：给定上下文 C，前瞻器采样 K 个候选延续 {c₁...cₖ}（可用温度采样 / 规划模型 / 工具调用候选集）。
2. **分歧度计算**：对每个候选编码 eᵢ = embed(cᵢ)，算两两余弦距离：
   - `D = mean(pairwise_dist) + λ·max(pairwise_dist)`（或用轮廓系数 silhouette）
3. **路形映射**（分歧度 → 几何）：
   - `D < ε₁`（如 0.15）→ **直道**（各走向高度一致，无需决策）
   - `ε₁ ≤ D < ε₂`（如 0.40）→ **缓弯**（有轻微分歧，微调方向）
   - `D ≥ ε₂` → **分岔路口**（K 个走向各成一支，分支数 = 主要聚类数）
4. **路生成**：把每个候选延续映射成路上的一个节点/分支，路形**动态铺开**。

**关键洞察**：
- 路不是前端画死的，是**分歧度的直接可视化**。
- "直道"= 模型很确定；"分岔"= 模型面临真实选择，需要用户决策。
- 这让"前方有没有选择"在生成前就可见——**决策不阻塞**。

### 3.3 阶段三：行驶（DRIVE）

- 载具沿生成的路行驶，位置 = 进度。
- **任务挂件**：后台真正在执行的任务（见 §4）浮成 3D 挂件。
- 前方分支可点击变道（点 3D 节点或底部导航条）。
- 后视镜 = 已通过节点的空间轨迹。
- 速度滑杆/暂停 = 用户掌控节奏。

## 4. 任务执行挂件（Task Widgets）

**问题**：后台 agent 在跑一堆活儿（工具调用、子 agent、数据处理），用户看不到，不知道"它现在到底在干嘛"。

**方案**：每个后台任务 = 一个 3D 挂件，悬浮在对应路段的上方/侧方。

**挂件信息**：
- 任务名（白话，如"正在检索资料库"）
- 状态：运行中（脉冲发光）/ 完成（绿勾）/ 失败（红闪）/ 等待（灰）
- 进度条 / 百分比
- 点击 → 展开详情（入参/出参/耗时）

**3D 呈现**：
- 挂件锚定在**它服务的路段节点**附近，位置随路段推进。
- 多个任务可并行，挂件并排悬浮。
- 用 DOM 投影法：3D 锚点 → 屏幕坐标 → DOM 卡片，保证文字清晰可交互。

**与前瞻推理的关系**：
- 前瞻推理预测"可能做什么"（路形）；
- 任务挂件显示"实际在做什么"（挂件）；
- 两者对照 → 用户能验证"规划 vs 实际"是否一致。

## 5. 状态机

```
全局：ALIGN → FORECAST → DRIVE → (到达终点) → 总结

ALIGN:
  生成路标 → 展示(术语+白话) → [用户点白话解释] → 确认对齐 → FORECAST

FORECAST:
  采样K候选 → 算分歧度D → 映射路形(直/弯/岔) → 铺路 → 出发 → DRIVE

DRIVE:
  行驶 → 到达节点 → 分支决策
        ├─ 沿主干继续
        └─ commitBranch(变道)
  全程：任务挂件随路段更新
```

**数据结构**：
- `passedNodes`：已通过节点 → 后视镜
- `committed`：已选分支 → 防重复变道
- `journey`：动态路径（变道时插入分支点）
- `signs`：路标（术语+白话），认知对齐产物
- `divergence`：分歧度 D，路形依据
- `tasks`：后台任务挂件列表（name/status/progress/anchor）

### 6.4 WebSocket 通信协议（v0.3）

|------|------|------|
| `forecast` | `type`, `context`, `k` | 发起前瞻推理，后端推演 K 个候选走向 |
| `ping` | `type` | 心跳保活 |

**服务端 → 客户端**：

| 消息 | 字段 | 说明 |
|------|------|------|

| 路由 | 方法 | 说明 |

### 6.5 向量空间投影（v0.4）

v0.3 的分支位置是程序化生成的（固定角度扇形展开），不反映语义相似度。v0.4 引入**力导向布局**，让 3D 空间位置直接反映 embedding 相似度。

**算法：力导向布局（Force-Directed Layout）**，纯 numpy 实现：

```
初始化：候选向量随机分布在球体内

迭代 N 次（默认 200）：
  1. 排斥力：所有节点两两排斥，力 = repulsion / d²
     → 语义差异大的分支彼此远离
  2. 吸引力：余弦距离 < eps（默认 0.35）的节点互相吸引
     → 语义相近的分支自然聚拢
  3. 弹簧力：向主干道锚点拉，力 = spring × (anchor - pos)
     → 分支不会飞太远，保持可读性
  4. 更新速度：v = v × damping + force（阻尼 0.9 慢收敛）
  5. 更新位置：pos += v（限速防止发散）

归一化：坐标缩放到半径 8 的球体内，前端直接可用
```

**参数调优**：

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `attraction` | 0.8 | 吸引力强度 |
| `repulsion` | 2.0 | 排斥力强度 |
| `spring` | 0.05 | 锚定弹簧强度 |
| `damping` | 0.9 | 阻尼，0.9 = 慢收敛稳定 |
| `eps` | 0.35 | 吸引距离阈值 |
| `radius` | 1.0 | 初始随机分布半径 |
| `iterations` | 200 | 迭代次数 |

**验证结果**：

| 场景 | 相似节点距离 | 正交节点距离 | 比例 |
|------|-------------|-------------|------|
| 相似 + 正交 | 0.37 | 12.00 | 32× |

语义相近的候选在 3D 空间中距离近 32 倍——这就是"向量空间即道路"的物理直觉。

**后端集成**：`forecast_result` 和 REST API 的每个 candidate 增加 `pos3d` 字段，前端 `generateRoad()` 直接使用真实投影坐标渲染分支位置。

### 6.6 多智能体协同可视化（v0.5）

#### 核心理念

当前系统是"单载具 + 静态分支"：主智能体沿主干道行驶，分支是可选的备选路径。v0.5 把它升级为**多载具并行预览**——每个分支上同时有一个小型预览载具在行驶，让你在 3D 空间里一眼看清"所有可能的走向各自走到哪里"。

这不是简单的装饰。它把"前瞻推理"的结果从"一组路标文字"变成了"多辆车同时在不同路上跑的真实态势图"——你不需要想象，直接看见。

#### 实现

| 组件 | 作用 |
|------|------|
| `AGENT_DEFS` | 智能体定义：名称、颜色、图标、角色 |
| `buildPreviewAgents()` | 为每个分支构建一个半透明预览载具（核心球 + 辉光） |
| 预览动画 | 每帧沿分支从岔口到终点 lerp，t 从 0→1，透明度脉动 |
| `updateAgentPanel()` | 左侧面板实时显示各智能体进度（主载具 + 各分支预览） |
| 变道时 | 预览载具继续独立行驶，不干扰主载具路径 |

#### 交互模型

```
主智能体（青）        → 沿主干道行驶（你当前选择的路径）
预览载具 × N（分支色） → 沿各自分支同时行驶（所有可能路径的并行预览）

你看到的是：一条主路 + N 条支路，每条路上都有车在跑
```

#### 认知价值

1. **空间化预测**：不再需要读完所有分支文字，直接看哪条路"跑得快/跑得远"——语义相近的分支在 3D 中距离近（由投影算法保证），自然聚拢。
2. **并行态势感知**：多个 agent 同时执行（检索 + 代码 + 分析），各自的进度一目了然。
3. **决策不阻塞**：预览载具自动跑，你只需要看，不需要点。想变道时随时切。

#### 与真实多智能体系统的对应

原型中预览载具是**模拟**的（匀速 lerp）。真实落地时：
- 每个分支对应一个实际的 sub-agent 任务
- 预览载具的进度 = sub-agent 的任务完成度（由后端 `task_update` 推送）
- 多个 sub-agent 并行执行，前端用各自的预览载具实时展示

## 7. 视觉与 3D 设计

### 7.1 空间布局
- 主干道：沿 Z 轴发光管，承载主线，节点发光球。
- 分支：主干节点斜出的彩色光路，终点可点击节点 + 3D 路牌。

- Three.js + UnrealBloom 辉光；CatmullRom 平滑曲线；加性混合全息；

### 7.4 相机
- 自研轨道跟随：载具=车，相机=驾驶员视角，位于车辆后方（沿 yaw 前移 6.5m）；拖拽=环视，滚轮=缩放。
- **第一视角跟随（v0.9.5）**：行驶期间相机 yaw 持续对齐行进方向、pitch 固定 0.33；到达后自动入场对位（`approachTheZ`，dist≤15m）看清新落位；焦点随车连续跟随（lerp）。

- **主轴绑定（v0.9.5）**：空间路形沿旅程主轴（travelYaw）展开，相机与空间的关系由「相机朝向决定路形」改为「已走路径决定路形」，方向感由空间本体承载。

## 8. 认知依据：为什么 3D 有效

1. **并行预览 vs 串行等待**：3D 把"未来"和"现在"放同一视野，2D 列表只能看"现在"。
2. **空间记忆 > 序列记忆**：人脑记"路径/位置"远强于"第几句说了什么"，后视镜轨迹比聊天记录易回想。
3. **深度线索降认知负荷**：距离=时间=重要性，天然排序，2D 需额外标注。
4. **具身感提掌控感**：载具+方向盘让"我在主导"增强，降低智能体使用焦虑。
5. **分歧可视化（新）**：把抽象的"模型有多不确定"变成肉眼可见的"直道 vs 分岔"，降低决策不确定性焦虑。

## 10. 风险与边界

- **不要过度游戏化**：3D 是手段不是目的，复杂数值/精确文本仍需传统面板辅助。
- **前瞻推理成本**：每次推演 K 个候选要额外算力，需控制 K 和频率，可只在"关键决策点"触发。
- **分歧度阈值**：ε₁/ε₂ 需按领域校准，太敏感→满地分岔，太迟钝→该分不分。
- **性能**：辉光+粒子+高分辨率管体+DOM 投影挂件在低端设备会卡，需分级渲染。
- **可访问性**：纯 3D 对视觉障碍用户不友好，需保留 2D 等价视图。
- **分支爆炸**：前瞻分支过多会 clutter，需聚类 + 限制显示数量。
- **白话解释质量**：路牌白话解释若不准，比没有更糟，需对齐验证。

## v0.9.6 工作日志（2026-11-06，用户高优反馈「选项不够丰富 + 刚开始短暂显示上一版套路」）

### 两条用户反馈的根因与修复

**反馈一：选项不够丰富**
三条独立割裂的「阉割链」叠加导致候选池被层层截断到 3 个：
1. 前端 `k=3` 且 `slice(0,3)`
2. 后端 `/api/forecast` 的请求级 `k` 没透传进采样器（`server.py` 硬写 `SpeculativeForecaster(k=4)`）
3. 旧快速通道精修 `refinsFutureSigns` 同样只拿 3 个

修复：`core.py` `forecast(context, k=None)` 接受请求级 k 并以 `kk = k if k else self.k` 优先；
`server.py` 端点 `fc.forecast(context, k)` 透传；`core.py` 默认 `k=5`；
前端 `runForecast` 与 `autoExploreNext` 统一请求 `k=5`；兜底池扩到 6 条 `slice(0,5)`。

**反馈二：刚开始短暂显示上一版套路**
旧 `autoExploreNext` 有 fast=1 快速通道：先用本地关键词模板（整理结论/继续深入那套）亮牌，
几秒后 LLM 精修回来才换牌——用户短暂看到的牌面就是「上一版套路」。
重写为：取消两段流，等待期只立一块中性灰占位牌（`paintPendingSign`，branchId=-9，
不在 `pickBranch` 未来牌点击区间内且被 `clearFutureSigns` 一并清理），结果回来一次性立 5 块
真正会话相关的牌。

### 修复过程中发现的两个真实 bug
1. **作废判据自废**：`autoExploreNext` 的 fetch 回调里 `!_futureCandidates.length` 恒为 true
   （入口刚清空），导致结果永远被丢弃 → 改为 token 判据（`_futureToken` 每次递增）。
2. **activeBranch 未复位**：执行链跑完后 `activeBranch` 仍停留在已走完分支的 idx，
   导致回调里 `activeBranch >= 0` 恒真，新牌被永远作废 → `finishExecution` 里
   `autoExploreNext` 前加 `activeBranch = -1` 复位。
